## Decisions

Each is the spec's, a rule's or a note's. The plan decides nothing new except where a Question says so.

- **D1. Names, hash id, no tag.** `Modules.Saving *Saving` (the Go line is appended after the pointers that exist), `World.saving *saving`, the file `saving.go`, the package `internal/saving`. The hash id is **23**; its pair goes in `pairsLastModules` between 21 and 24. A non-nil module with no field writes `e.id(23); e.end()`: the module has three tunables, each written only when non-zero, so the presence is the whole contribution of a zero module. Inner ids in declaration order, recorded by E2 in spec-config.md 8.2.2: `Saving` `SafetyTicks` 1, `HurdleSpreadBP` 2, `CommitBandBP` 3; `Saver` `PrecautionShareBP` 1, `PrecautionCapTicks` 2, `HurdleBP` 3, `PaybackTicks` 4, `RepairBelowBP` 5, `Worth` 6; `ProjectWorth` `Class` 1, `PerTick` 2, `Count` 3. `Role.Saver` takes the next free `Role` id, **29**, with 28 reserved in the same edit for `Role.Cover` (INS, whose place in the `Role` row of spec-config.md 3.7.1 is before `Saver`), so the order in which the two modules are built cannot make them collide (Q6). A non-nil `Saver` block is written even when every field is zero, because an inert block opts a role into the measure (spec 8.4.1). `Worth` is written in class-ID order (the canonical copy sorts it, FR-CFG-096). **There is no checkpoint tag** (spec 13): the module has no state, and the row of spec-checkpoint.md 4.2 reads "SAV: none, and why" (E5). **The hash and the format leave `golden/off/`, the pinned hash and every existing checkpoint unchanged** because a module that is off writes nothing and no existing pack has a `Saver` block.
- **D2. Defaults are data, in `defaults.go`.** `DefaultSaving()` returns `SafetyTicks` 2, `HurdleSpreadBP` 20 000, `CommitBandBP` 2 000; `DefaultSaver()` returns `PrecautionShareBP` 0, `PrecautionCapTicks` 30, `HurdleBP` 15 000, `PaybackTicks` 180, `RepairBelowBP` 5 000. The loader (`config/mapping.go`) starts each table from the default and overwrites the keys it finds, as `DefaultSettlements` and `DefaultEmployer` do; a configuration built in Go states every field, so a `0` is the value 0 (a hurdle spread of 0, a repair gate of 0 = never repairs). Validation reads what it is given. No default is set from a source (N-018, N-027); the overlay's header says so.
- **D3. No state, no draw, no ledger move.** `type saving struct` holds derived tables only: per role with a block the resolved recipe indices of its project recipes (each with its class index, kind, `Capacity`, `Durability`, `Decay`, `WearPerUse`), the `Worth` rows resolved to class indices, and the per-(region, role) counts scratch of the tick. Nothing in it is saved, restored or hashed except through the configuration. The module draws no word (the hurdle spread is `Weyl32(AgentID)`), opens no account, writes no ledger row and registers no flow, so `random.go`, `ledger.go`, `internal/ledger/registry.go` and the pinned reason table are **not touched**. The supervisor's allocation of ledger reason codes 76 to 83 is unused by this row. (A note for the supervisor: `internal/ledger/checkpoint_test.go` pins 42 rows and plan-3-rsk's PR B result records that a code from `pinnedRows` upward is the code of a configured money flow, so a later reason takes its pinned row by position, not a number in that range.)
- **D4. The target is one place, with the plan's tier 2 as an argument.** `savingTarget(v, tier2)` returns `Floor`, `Goal` and `S*` (spec 3.2.2) and `DefaultStrategy.TradeWith` replaces `savings` by `S*` between `tier2 := t.tier2Cost()` and `t.allocate(cost, savings)`: `if v.Saving != nil { savings = savingTargetOf(v, savings, tier2) }`. `reserveMoney` in `strategy_work.go` (the work share, the survival rule) and the merchant's planner keep the flat reserve (spec 3.2.3, FR-SAV-003). **The spec has a contradiction this plan resolves (N-490):** 5.6.3 makes `Goal` depend on `Tier2_p`, the money the plan has committed to the project's inputs in this very tick, and FR-SAV-042 says the exported `SavingTarget(v)` returns what the default uses, but the view carries no plan. The exported form is `SavingTarget(v *AgentView, tier2 int64) SavingTargetResult`, as `DefaultCredit(v, p, tier2, duration)` takes the figures the view does not hold (CRD precedent); a read of saved state (the query, the snapshot rows, the counts of the event) passes `tier2` 0 (Q3). The difference is confined to the one tick in which a funded household buys its project's inputs (example A3, spec 16.5), and a test pins it.
- **D5. The `Saving` group and who computes it.** `AgentView.Saving *SavingView`, nil for a role with no block (the module off, or the role has none), set in both the `Work` and the `Trade` view (FR-SAV-028), holds `Block` (a copy of the `Saver`), the three module tunables, `Drawdown`, `Facilities` (own, in the region, ascending ID; CAP's `FacilityView`) and `Classes` (kind, `Durability`, `Decay`, `WearPerUse`, `Capacity` of each class a project recipe names). The world computes `Drawdown` from the ring at fill, through `w.welfare.at(id).AppendRecords(scratch)` and `welfare.Drawdown`, in the scratch the view already carries (NFR-SAV-002: no allocation in steady state). It is filled by one **nil-safe, unguarded** call at the end of `fillAgentView` (`w.saving.fillView(v, a, kind)` on a nil receiver returns at once), the form of CAP's `fillFacilities` (CAP hook 7): `fillAgentView` is at CCN 10 and a guarded branch would make 11. The drawdown costs `O(window)` per agent with a block and per view, so twice a tick; Q9 recommends no cache until the benchmark of Phase 2 shows one is needed (N-493).
- **D6. `Standing` and the clauses.** `RecipeView` gains `Needs` (class indices, no string), `Builds` and `Repairs` as small value structs (class, `Toward` or `Units`) and `Standing Reason`, appended at the end (spec 5.2.2). `Standing` is the first refusal of spec-infrastructure.md 4.2.2 other than `no_input` and `no_tool` that would apply were the inputs held, or empty, **derived by CAP's helper `standingReason`** (plan-3-cap.md: "builds the derivation helper and no view field"); SAV calls it when it fills a recipe with a clause. The request and the planned recipe.** `DefaultStrategy.Work` gains one guarded call: `if v.Saving != nil { if req, ok := savingRequest(v); ok { return req } }` (CCN 2 to 4). `savingRequest` returns the chosen project's request when the household is not barred, no project job is in progress, and the project's `MaxExecutions` is at least 1: one execution for a build and `MaxExecutions` for a repair, whatever the work share (spec 5.7); otherwise `ok` is false and the default's request stands. `TradeWith` gains one guarded call after `plannedRecipe`: a funded household's planned recipe is the project's (spec 5.6.4). ## Gate economics

- Full gates (gate R and gate F, `check.sh`, `full.sh`) run **once per PR, on the final head**, with `GOMAXPROCS=8`, and **one gate run at a time on the host**: earlyoom kills the 20-plus GB root test binary when two share the machine. While a gate runs, no other session starts one.
- During a phase, run only the focused tests and `go test -short -race ./...` (and `-run` on a phase's own tests); do not run gate R or F per phase, per commit or per fix.
- If a gate run fails, fix, then rerun only the failing package; the full gates are rerun once more on the final head if the fix touches non-test code outside that package.
- `gomu` only inside Docker with `--cpus=4 --memory=16g --memory-swap=16g -e GOMAXPROCS=4`, per new file, never on the host; it does not overlap a gate run.
- A scenario test that keeps per-tick snapshots must not keep them for every parallel seed (the S113 lesson): S143 to S146 keep counters and the events, not snapshots. The drawdown is `O(window)` per agent with a block, twice a tick: a scenario with 1 000 savers and a window of 3 650 runs 7 million additions a tick, so the multi-seed scenarios use the default window and few agents.
- `examples/realm` `TestServe_*` can time out under `-race` when several gate runs share the machine; a rerun alone settles it.
