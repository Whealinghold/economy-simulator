## Scope

This plan builds the tenure module. A **title** is a share, in basis points, of the snapshot stock of one endowment, held by one agent or by the estate pool of the endowment's region. Before the ration of P2.6 each holder has an **entitlement**, the largest-remainder apportionment of the stock; the ration is four tiers (own, commons, let); rent is a ledger transfer of the new reason `rent` for the units drawn from let units; the posted rent may move by a bounded step at the new position P8.3a; titles move by configuration, by the public call `TransferTitles` and, at a removal, to the pool. It has no draw, no new account and no boundary flow. It is off unless `Config.Modules.Tenure` is non-nil, and then it needs `Modules.Resources`.

## Decisions

- **D1. Names, hash id and tag.** The Go names are `Modules.Tenure *TenureConfig`, `World.tenure *tenure`, the file `tenure.go`, the package `internal/tenure`. The scope `Tenure` resolves to `TenureConfig` through `scopeAlias` in `registry_test.go:94`, a two-entry map today (Subsistence, Polity); the entry `"Tenure": "TenureConfig"` is a Phase 3 edit (`spec-config.md` 3.7.1). The hash id is the position of `Tenure` in the `Modules` row of `spec-config.md` 3.1 (the ids are 1-based, `Settlements` 11 to `Technology` 24, `Estates` 25); `hash.go` already writes `Storage` 12, `Employment` 13, `Polity` 19 and `Estates` 25, the row of `spec-config.md` 3.1 reads Settlements 11, Storage 12, Employment 13, **Tenure 14**, Credit 15, Risk 16, Infrastructure 17, Insurance 18, Polity 19, so the hash id is **14**. `pairsModules` writes pairs "in ascending id order ... at the place of its id" (`hash.go:421`), so the pairs of `Tenure` go in `pairsLaterModules` (`hash.go:474`) between `Employment` (13) and `Polity` (19); only the `Modules` field order, `canonical` and `modulesOn` are appended in Go order (architecture.md 2.10.5). A pinned encoding test sits beside the `hash.go` tests (`TestHash_TenureEncodingPinned`: id 14, then the inner ids). The inner ids are the declaration order of each struct (`spec-config.md` 8.2.2): `TenureConfig` `Terms` 1, `Holdings` 2, `RentStepBP` 3, `RentFloorBP` 4, `RentCeilingBP` 5, `OwnUseExempt` 6, `MaxHolderShareBP` 7; `TenureTerm` `Region` 1, `Resource` 2, `Rent` 3, `Closed` 4 (the `Has` flags are exempt, as `Endowment.HasCapacity` is); `Holding` `Region` 1, `Resource` 2, `Holder` 3, `ShareBP` 4; `HolderRef` `Kind` 1, `Role` 2. `spec-config.md` 8.2.2 lists none for LND today (the same gap POL found; POL's plan chose and documented them in `hash.go`); E4 adds the sentence (Q7). The checkpoint tag is **25** (`notBuiltSections` has the row); the module has one section and writes no field in the agent record (N-128).
- **D2. State is module state, not agent state** (N-244). `tenure` holds: per endowment cell a sorted holdings slice (holder agent ID, share), the posted rent, the rent scale, the two diagnostic runs, and per-tick scratch (entitlements, tier grants, supplies, the attribution list, the counters). The module's audit method is `audit` (not `auditModules`: that name is the `World` method of `moneyflow.go:865`, see H4). The agent type gets no field (`TestAgent_HoldsNoMoneyQuantityOrRegion` keeps passing). A holder is the agent ID; the pool is the estate pseudo-agent whose ID equals its `RegionID` (`spec-regions.md` 3.6). Derived and never saved: the commons share, the entitlements, the tiers, the supplies, the rent in force, the key (14.1.1).
- **D3. Files.** The module file is `tenure.go`. Lizard (`-C 10 -a 8 -L 100`, N-243) will force continuation files for a module with six touch points. Phase 1 E1 names them before code: `tenure_validate.go` (VAL and the warnings), `tenure_ration.go` (P2.3, P2.6, P2.7: the tiers, the charge, the reasons), `tenure_transfer.go` (construction step 8a, the removal step, `TransferTitles`, the queries) and `tenure_report.go` (events, logs, snapshot rows, the codec). Each maps to the area code LND and its tests carry the `Requirement:` lines (architecture.md 2.6). `internal/tenure` and `tenure.go` are in `AGENTS.md` and 2.6 already; only the continuation files are added, in one edit to both lists with a fresh RULE-TAG (the same edit STO made). A file that stays inside the limits is not split.
- **D4. The pure package** `internal/tenure` is stdlib, `internal/checked`, `internal/ordering` and `internal/endowment` (for the ration of RES 5.3.2) only, over primitive slices (architecture.md 2.9): `Apportion`, `Tiers` (the four tiers with the let demand clipped by cash), `Attribute` (the two-pointer walk of 4.4.2 and the lessor supply of 4.4.1), `RentInForce`, `Charge` (the largest `k` whose rent the principal's balance covers and the reservation against its other starts), `Step`, `Cap` (the share check). The module needs `internal/endowment` to export or share the rule 5.3.2 it already has; Phase 2 checks whether `endowment.Ration` can be called per tier as it stands (the spec says each tier is "the rule of RES 5.3.2 on a different supply"). If it can, no `internal/endowment` file changes; if not, the smallest additive change is made there and listed in the PR.
- **D5. Rent is one internal ledger reason pair, not a money flow** (`spec-land.md` 5.1, 5.8; N-107). `rent` and `title_sale` are added to `internal/ledger/registry.go`, to the `reasonNames` table of `ledger.go` and to `event.go` as constants. The charge goes through one function in `tenure_ration.go` that takes (payer, payee, units, rent); a later FIS hook for a tax on a reason (N-187) is one call in it.
- **D6. No new draw, no new random site** (FR-LND-036). Every tie goes by the stateless key of RES 5.3.3 and then the agent ID. The proof is a text search for a draw in the tenure files and the equal-stream test of FR-LND-006.
