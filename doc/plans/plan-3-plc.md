- **D2. The canonical order.** Actors sort bytewise by ID, levers by ID within the actor, schedule steps by (`Lever`, `At`) and reactions by `Lever`; the sort is the method `(m *PolicyConfig) canonical()` called from `Config.canonical` (as `Fiscal` has one). The `ActorID` and `LeverID` are indices in these orders (FR-PLC-003); they are not stable across configurations and nothing persists one (the checkpoint writes an index only inside one configuration's hash).
- **D3. The built-ins are not exported values.** Spec 4.4.1 names `Schedule`, `Rule` and `Directed` as root values, and `Directed` is the agent strategy (`strategy.go:222`). A consumer never builds a built-in (it is made from an actor's row and registered by the world under its reserved name), so only `HoldPolicy` is exported, which is the one that architecture.md 4.5 requires as the default and its assertion. The three others are unexported (`schedulePolicy`, `rulePolicy`, `directedPolicy`) each with `var _ Policy = ...`. The reserved names `hold`, `schedule`, `rule`, `directed` are the strings (spec 4.4.1) and `WithPolicy` refuses them with `ErrDuplicateID`. Phase 1 edits spec 4.4.1, 20 and the glossary to say so (Q1).
- **D4. Application through the owners' internal forms, with `CausePolicy`.** At a decision the world builds, from the checked entries, one list per kind: a `[]EdgeStatus` for every key of every `edge` lever that differs, a list of (from, to, mode, bp) for `transit` and a list of (flow ID, bp) for `flow`. It applies **edge first** in one `setEdgeStatuses(changes, CausePolicy)` call (the graph is rebuilt once for the whole application, FR-PLC-043), then each transit key through `setTransitFactor(..., CausePolicy)` in ascending key order, then each flow through `setScaleOf(id, bp, CausePolicy)` in ascending flow-ID order (6.4.2). Each call is checked at validation to be unable to refuse (6.1.2), so a refusal is `invariant(...)`, as the public setters treat it (`integration_slots.go:246`). The `EdgeStatus` of a group is the whole value: the factor from the lever's number and `Closed` from the entry (the lever's own state when the entry is `unchanged`); the number and the flag are written together. A tick's application does not call `Slots()`.
- **D5. The position.** `p03aPolicy` is one guarded call, `if w.policy != nil { w.p03aPolicy() }`, in `positions()` between `p02` and `p11Moment`; `"P0.3a"` leaves `notBuiltPositions` and `{"P0.3a","PLC",line}` joins `positionList`. P0.3a runs before any position that reads a slot, so the actor's write is indistinguishable from a consumer's call made before the step (7.1.2). `positions()` is at CCN 8 and 22 NLOC at this head (`lizard`, measured), so one guarded call makes 9 and needs no refactor-first commit; Phase 1 re-measures, because CAP, SAV and INS may add calls to the same function first, and if the count would pass 10 the first commit splits its head as `positionsFlows` and the others were split.
- **D6. The view and its cost.** A view is built fresh per call (FR-PLC-025): the levers from the derived tables and the slots' current values (3.4.4: the first key of a group), the `Treasury` from the ledger account of `World.TreasuryAgent`, and, with `ReadsRegions`, a `RegionState` per covered region that is not an outside node. The builder needs the body of `World.Region` **without** `guard()` (a call from inside a step is `ErrInStep`): a refactor-first, pure-move commit splits `Region` into the guard and `regionState(g)`, which `Region` calls; `Region`'s behaviour and tests do not change. `prepareAnchors` reads every agent (NFR-PLC-002 and the comment of `Region`): the plan prepares the anchors **once per P0.3a pass** (the first actor that reads regions) and shares them between the actors of that tick, since the state does not change between two actors' views (an earlier actor's writes are slot values; whether a cost anchor reads the graph or a transit factor, which an earlier actor's edge or transit write changes, is **unverified**: Phase 5 reads `prepareAnchors` first and, if it does, re-prepares after any application that wrote an edge or transit key; `TestView_PassEqualsSeparateViews` pins the result against separate views). A `rule` whose only gauge is `treasury`, `hold`, `schedule` and `directed` build no region state (5.4.2). The cost of a `ReadsRegions` actor is one snapshot's scan per decision, measured in Phase 5 and reported (N-015), never optimised blind.
- **D7. Key lists are derived once.** At construction `newPolicy` resolves each lever to its keys: a flow to its position (`flowKey`) and ID, an edge to its `EdgeID` (a pair, or `Polity.Between(g, J, K)` and `Between(g, K, J)` merged in ascending `EdgeID` for `Against`, spec 3.4.3), a transit to (from, to, mode). They are dense slices indexed by (actor, lever); they are never saved and never rebuilt (the tree is fixed, POL position 9). A group that expands to nothing is legal and warns (`lever_no_keys`).
- **D8. The due test** is `(t + ordering.Bucket(int64(actor), every)) mod every == 0` (FR-PLC-051), computed per actor per tick as a pure function (no table). The tests read the worked values of spec 14.1 (`models/plc/worked.py`: buckets 0, 4 and 24; due ticks 0 and 6 mod 10 and 6 mod 30) and fuzz it against a reference.
- **D9. The checks and the arithmetic live in `internal/policy`.** `Decide`'s result is converted inline (architecture.md 2.9) to primitives `(lever, bp, closed)`, with the lever table as primitives `(kind, min, max, maxStep, mayClose, current, closedNow)`, and returns one outcome per entry plus the tally and the values to write. The rule's product uses `checked.MulDiv` (the truncating 128-bit form), not a private copy (the spec's "own product until N-019" is met by the shared `internal/checked`, which exists; Phase 1 edits 8.3.4 to say so). The saturating sum of `v + d` and the move toward a bound from outside it are in the package with their tests (FR-PLC-041, 062).
- **D10. The mailbox** is state in `policyState`: one sorted slice of `LeverSetting` per `directed` actor, replaced whole by `DirectPolicy`, read and cleared at the actor's decision whatever the outcomes (8.4.1). `DirectPolicy` is in `policy_state.go` and delegated from `integration.go` (`World.DirectPolicy` is the public method; its checks in the order of 9.1.2 use `w.enter`, `slotKeys`' style and `argError`). `Snapshot.Actors` carries `Pending` (the count). Atomic, no draw, no event.

## Gate economics

- Full gates (gate R and gate F, `check.sh`, `full.sh`) run **once per PR, on the final head**, with `GOMAXPROCS=8`, and **one gate run at a time on the host**: earlyoom kills the 20-plus GB root test binary when two share the machine. While a gate runs, no other session starts one.
- During a phase, run only the focused tests and `go test -short -race ./...` (and `-run` on a phase's own tests); do not run gate R or F per phase, per commit or per fix.
- If a gate run fails, fix, then rerun only the failing package; the full gates are rerun once more on the final head if the fix touches non-test code outside that package.
- `gomu` only inside Docker with `--cpus=4 --memory=16g --memory-swap=16g -e GOMAXPROCS=4`, per new file, never on the host; it does not overlap a gate run.
- A scenario test that keeps per-tick snapshots must not keep them for every parallel seed (the S113 lesson): S155 to S159 keep counters and the events, not snapshots. A `ReadsRegions` actor at `Every` 1 over `five` scans the world each tick: the scenarios use the cadence of 14 (`Every` 30), and the cost is measured once and recorded in the PR (NFR-PLC-002).
- `examples/realm` `TestServe_*` can time out under `-race` when several gate runs share the machine; a rerun alone settles it.
