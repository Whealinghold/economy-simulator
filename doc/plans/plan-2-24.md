## Decisions

- **D680 (names).** `examples/realm/` is the first consumer (a fantasy realm, the setting `AGENTS.md` names), `examples/colony/` the second setting (the crater colony of REF 4.4.7). Both module paths are `github.com/Whealinghold/economy-sim/examples/<name>`, each with `replace github.com/Whealinghold/economy-sim => ../..` as the inspector has; plan 22 creates `go.work` and must list `.`, `./otelobserver` and the existing `./examples/inspector` (in workspace mode a module not listed fails to build; the fix to plan 22 D640 belongs to plan 22), so this plan adds only `./examples/realm` and `./examples/colony` (owed edit, Phase 1). The `replace` lines keep each example building with `GOWORK=off`. Source: `architecture.md` 2.6 ("each example is its own module"); roadmap Stage 2 last row; owner's delegation of 2026-10-22.
- **D681 (the inspector).** `examples/inspector` is kept unchanged: it is a read-only developer tool over the packs in `testdata/chains/` (report mode and a TUI), not a consumer. It already shows `Run`, `Snapshot` and the events through the public API and its tests run today. It does not satisfy `vision.md` 5 item 5 ("a complete server ... and the RPG data pack runs") because it has no player, no shock, no save and no restore, and it reads the fixtures of the repository instead of carrying a pack. The new examples are siblings; none imports another (a module cannot import a `main` package, and a shared helper would couple two examples). Source: `vision.md` 5 items 3 and 5; `architecture.md` 1.3.
- **D682 (the realm pack is `five` in the setting's words).** Proposed, pending the owner's ruling that gates Phase 3 (R2): the first consumer's world is `five` after plan 8's rebalance: 5 regions, 5 000 households, 30 commodities, 45 recipes, 20 roles with groups (`vision.md` 6, REF 4.4.4); `spec-roadmap.md` describes the RPG data pack as content kept separate from the reference chain, so the owner may instead order an authored pack. The pack of `realm` is that chain with every identifier renamed through one table (`examples/realm/pack/names.txt`, Phase 3) and the region names and the display names set in the setting's words; nothing is added to the economy. The renaming keeps the viability, the census and the warm start of `five` (the same programme under other labels), which is the evidence the pack inherits; any change of the economy would void it and would be plan 8's. Setting vocabulary (grain, ore, silver) is allowed here because the example is flagged setting-specific content (`spec-roadmap.md`, "Deliverables that are not specs"); the core stays generic (`AGENTS.md`). A test proves the renaming: the solver gives the same `surplus_bp`, `pivots` and census counts as `five` after mapping the names (Phase 3). Source: `vision.md` 2; `spec-roadmap.md` "Deliverables that are not specs"; REF 4.4.4; R2 lists the alternative. The owner's delegation of 2026-10-22 covers plan order only, not content.
- **D683 (the all-on pack).** `testdata/chains/all/` holds the layers that turn on every version 1 module on `five`, in the order of the `Modules` pointers (`spec-config.md` 3.1): demand, money supply, population, transport, resources, information, external, subsistence, migration, merchants, and the `Estates` part (the 25th, built by plan 7). Each module's dependencies precede it in this order (merchants need transport and information, migration needs information). It is written once, by copying each module plan's overlay tables (the `five`-sized layers `trade-five.toml` (plan 3, edges), `transport-five.toml` (plan 12, modes, haul commodity, vehicle, carrier groups) and `information-five.toml` (plan 13, module table and `informed` only), in that order) and using `resources-five.toml` and `resources-five-binding.toml` of plan 9 (D398) as they are, and retargeting the region and role identifiers of the overlays that sit on `one` or on the two-region variant (`external.toml`, `own-use.toml`, and `merchants.toml`, which is region-keyed on two regions and is the template for the retarget) to `five` (R4); the results are new layers under `testdata/chains/all/`, never edits of the module plans' files. The warm start of the pack is `warm-five.toml` (the solver table of the modules-off programme, as plan 8 recorded it, with the solver options that produced it); `WarmStart` is part of the hash, so the all-on world and the modules-off `five` differ in hash only through the module layers. The `realm` configuration is this pack under the rename of D682. The list of layers is one table in `all_pack_test.go` (`allLayers`) that every all-on test reads; a module added in Stage 3 appends a layer and moves `golden/all/` once, with the explanation of testing.md 7.2. Source: `architecture.md` 10.4 (all-on golden); roadmap Stage 2 "Each module file ships ...", and the all-on golden and fixture left to this plan by plans 2, 3, 15, 16.
- **D684 (the warm start of the example).** The module `realm` embeds the cold layers (`//go:embed`) and calls `economysim.SolveSteadyState` once at start-up on the modules-off layers (the programme `warm-five.toml` was solved from, the same options), then sets `cfg.WarmStart` to the returned table; `TestPack_StartupSolveIsWarmFive` proves that table equals `warm-five.toml` under the rename. No warm-start TOML is shipped, because the writer that produces the warm documents is a test helper of the root module (FR-REF-007), not public API, and `architecture.md` 1.3 forbids reaching for it. The solve is outside the tick budget (`spec-scale.md` 6.1); its time is printed at start-up. `colony` ships its warm document, which is a byte copy of `testdata/chains/second/warm-second.toml` (D687). Source: `spec-viability.md` 7.1 ("`NewWorld` never calls it"); `spec-scale.md` 6.1.
- **D685 (the server).** `realm` is a stdlib `net/http` JSON server. One type, `Game`, owns the `*World` behind a `sync.Mutex` (a world is not safe for concurrent use, `architecture.md` 12.1, 12.6): every handler locks, calls the world, unlocks. The only goroutine the example starts is the optional pacing loop in `main.go` (a `time.Ticker`; the library has no clock, `AGENTS.md` "Deterministic"). Handlers are thin; `Game` methods carry the logic, and tests drive `Game` and the handlers through `httptest` with no ticker and no sleep (`architecture.md` 10.5). Money crosses the wire as `int64` minor units plus the formatted string of the RPG preset (`denomination`, FR-CUR-017); no float is computed. Types carry no struct tags in the core (`architecture.md` 12.6); the example's own wire types may.
- **D686 (what the server shows).** The calls of `spec-integration.md` 8, in that order: load the pack and `Warnings()`; `AddAgent` for the player before the first step; `Run` to give the market a history; per game step, `Agent(player)`, `Market`, `Region`, the events of the last step from an `Observer` that keeps the player's own events; `Direct` with the player's orders; the shocks `SetYieldShocks` (a failed harvest) and `SetEdgeStatuses` (a closed road); `Step`; `Checkpoint` and `RestoreWorld` with the consumer re-registering its observer (extensions are not saved, `spec-integration.md` 8). The routes are listed in Phase 4. Field and type names (`NewAgent`, `Directive`, `AgentState`, `YieldShock`, `EdgeStatus`) are those plan 17 builds (plan 17 is on disk); Phase 1 re-reads them against the code. Source: `spec-integration.md` 4.1, 4.3, 5.1, 6.2, 8; `notes.md` index entry "the first consumer example must show a player".
- **D687 (the second setting).** `colony` is the crater colony of REF 4.4.7 (10 commodities, 10 recipes, 5 roles, 1 000 households, two seasons), shipped as an embedded copy of `testdata/chains/second/second.toml` and `warm-second.toml`. The copy is guarded by `TestExamples_PackCopiesAgree` in the root module (byte equality, so the example cannot drift from the fixture whose X4 test runs). - **D688 (the guard on `internal/`).** Go lets a nested module whose import path lies under the parent's path import the parent's `internal/` packages, so `architecture.md` 1.3 is not enforced by the toolchain. `TestExamples_NoInternalImports` (root module, `examples_guard_test.go`) parses every `.go` file under `examples/` with `go/parser` (imports only) and fails on any import path under `github.com/Whealinghold/economy-sim/internal/`. It also fails if an example imports another example. `TestExamples_PackCopiesAgree`, `TestExamples_NoInternalImports` and the root benchmarks read files under `examples/` from the root module, which testing.md 10.2 discourages; they are the only such tests, they read bytes and import lines only, and the exception is stated here for the reviewer. Source: `architecture.md` 1.3, 2.7; the existing guard `TestImports_StdlibAndLayers` scopes the core and does not look at `examples/`.
- **D689 (the tables).** The `five` rows of REF 7.5 (400 ticks, seeds 1 and 2) and 8.2 (golden 400 ticks seed 1; determinism seeds 1 and 2; checkpoint 200+200), and the `all` rows (same lengths), are added to the existing table-driven tests (`invariants_test.go` `invariantTable`, `golden_test.go`) where an earlier plan has not added them, and the determinism rows are a new test, `TestDeterminism_FiveAndAll` (`determinism_test.go`): it runs the short case list (bare, observed, `Run(400)`, `Run(1)` + `Run(399)`, audit on), taken from `detCases(true)` by name, on `five` and `all`, seeds 1 and 2, and does not call `detCases(false)` (which would be too slow on 5 000 agents, notably under emulation); no test is rewritten (REF 7.5 last paragraph, N-295). The `five` and `all` rows are the only five-sized rows of these tables; a five-sized row from another plan (plan 14 adds a `five` migration world) is skipped under `raceEnabled` like them, or sized down by its plan. `testdata/golden/off/five.txt`, `events-five.txt`, `five.positions.txt` are recorded with every module off, from the rebalanced `five`, with the explanation of testing.md 7.2 as new files. `golden/off/one*.txt` do not move. Source: REF 7.5, 8.2, 8.5, FR-REF-029, FR-REF-032; testing.md 7.1.1.

- **D691 (two architectures).** Bytes are fixed by checked-in files that both architectures compare against, never by a second file (REF 8.6, plan 1 D237): a golden that differs on arm64 is a defect in the code (no float in results, `architecture.md` 3.5), not a second golden, and `-update` is run on the recording architecture (amd64) only. - **D692 (the cost budget).** The budget is `spec-scale.md` 6.2 as plan 4 left it: NFR-SCL-002, `c_0 + |T_a| * c_t` per agent, which for `five` (5 000 agents, mean `|T_a|` 7.7) is about 53 ms a tick (6.3, REF 4.4.4). No test asserts the time: testing.md 10.2 forbids wall-clock dependence, 8.2 says benchmarks report and never fail CI, and architecture.md 10.5 requires every test to pass under `-race`. The figure is a benchmark result recorded against `x3.ms_per_tick` of `bands/five.toml` (REF X3) and read by the owner. REF X3 asks for an assertion; the owed edit to X3 (Phase 1) turns it into a recorded figure. Source: `spec-scale.md` 6, 12 item 1; REF X3; `vision.md` 5 item 6; N-030, N-300.
