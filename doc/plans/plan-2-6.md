## Decisions

Each has its source. A plan decides nothing the specs decide; the decisions below are the plan's choices where a spec is silent or a code fact forces a shape, flagged "owed" when a spec edit must follow (Phase 1).

- **D320.** Only the target kind `households` is built. `pool`, `stores` and `treasury` are recognised names whose module is not built, so a flow naming them is `ErrModuleDependency` (a stage fact: MON 12.1 says it for `pool` and `stores`; for `treasury` the nearest sentinel until POL, owed). Plan 7 adds the `pool` case in three places only: the kind switch of `validateMoneySupply`, `moneyFlows.recipients` and the tag 13 carry list (D337). Source: roadmap Stage 2 rows MON and EST (the pool is the EST row), MON 4.3, architecture 2.10.5.
- **D321.** The root file is `moneyflow.go` and the package `internal/moneyflow`, as architecture 2.6 and the roadmap name them; MON 22 says `moneysupply.go` (owed edit). Source: architecture 2.6, 2.10.1.
- **D322.** The core identities (MON 3.1, 8.2: `M` equals `M_init` plus grants less levies; `M_h + M_p + M_c = M`; money per household moves only with households and sectors) need no production code: `Ledger.Audit` already checks the zero total and the boundary identity, and `Snapshot` carries `Money`. They are asserted by invariant tests over seeds with `WithAudit` (FR-MON-001, 028, 046; Phase 5). The only identity code is the per-flow check of D333. Source: MON 8.7, 3.5.
- **D323.** Flow reasons are dynamic reasons of `internal/ledger`. The registry is a static `[NumReasons]` table and `Reason` is a `uint8`, so `ledger.Config` gains `Flows int` (a count, 0 = none) and the reasons `NumReasons + i` for flow `i` in ID order, each a money-only row: faucet from a boundary to an Agent or Estate account, sink from an Agent or Estate account to a boundary (MON 4.5.1, ledger 7.2). Constraints: (a) the existing `off [NumReasons][2]int`, `table` and every walked field stay as they are and the new state is nil slices at zero flows, because the position hash walks the `World` by reflection (poshash_internal_test.go D177) and `testdata/golden/off/*.positions.txt` must not move (architecture 2.10.5). Plan 5 D311 owns this layout rule (a declared reason is a bit of its row; no state is added to the walked fields), and the flow slice follows it; (b) `AppendFlows` and the root `boundaryRows` emit the flow block after the built-in reasons and before the `outside_*` block and every module row, the order of observability 4.4.1.2 (built-in, then flows in ID order, then the module rows by rank); there is no `flowsBefore` constant, the rank of the block is a row of the registry order of D311; (c) `Boundary`, `OpenBoundary`, `Transfer` and `slotOf` accept the dynamic reasons; (d) a flow reason has no goods row; (e) the plan-2 state bytes need no new code: the flow boundaries are opened by `newLedger` from `Flows` before `ReadState` runs, their balances are written with the boundary list in account order, and a pending total names its reason by the pinned code of plan 2 D246, which for flow `i` is `pinnedRows + i`, where `pinnedRows` is plan 2's fixed count of the full 7.2 table, so the saved flow code does not move when later plans declare reasons (never the Go number; the in-memory number `NumReasons + i` stays internal), checked against `pinnedRows + Flows`. Source: MON 4.5.1, 22 ("built at construction from the flow list"), ledger 3.4, 7.2.2, observability 4.4.1.2.
- **D324.** The boundary accounts of the flows are opened by `newLedger` right after the built-in group, in flow-ID order, as the flow accounts fill group 2 of plan 5's `newLedger`, so they are created before the `want_consumption` accounts, the estates and the agents (ledger 3.4.2, MON 4.5.1, N-226 row 2). The account IDs of a world with the module on therefore start after `B + flows`; nothing records an account ID of such a world in a golden or a fixture (verified in Phase 5 by grep over `testdata/`). A world with the module off is unchanged (`B = 1 + 7C`).
- **D325.** A flow ID equal to any reason name of the registry table of ledger 7.2 is `ErrReasonCollision`, whether or not that reason's module is built: the rule constant `reservedReasons` in `moneyflow.go` lists the 7.2 names. A guard test fails when a name of `reasonNames` (ledger.go) is missing from it. Source: MON 4.5.2, FR-MON-036.
- **D326.** Config types: `MoneySupply{Flows []MoneyFlow}`, `MoneyFlow` and `FlowTarget` exactly as MON 4.1, with `Kind`, `Per` and `FlowTarget.Kind` as strings and exported constants `FlowGrant`, `FlowLevy`, `PerTick`, `PerYear`, `TargetHouseholds` (`TargetPool`, `TargetStores`, `TargetTreasury` are their plans'). The empty `Per` means `tick`; `canonical()` rewrites `""` to `"tick"` so the effective configuration and the hash do not depend on the spelling (NFR-MON-003). Hash ids (owed row in spec-config 8.2.2): `Modules.MoneySupply` 2 (its position in the row), `MoneySupply.Flows` 1; `MoneyFlow`: `ID` 1, `Kind` 2, `Target` 3, `Amount` 4, `Level` 5, `RateBP` 6, `Exempt` 7, `Per` 8, `Start` 9, `Until` 10, `Limit` 11, `NotIncome` 12 (`Label` presentation only, never an id); `FlowTarget`: `Kind` 1, `Region` 2, `Role` 3 (`Store` 4 and `Jurisdiction` 5 are STO's and FIS's). Flows hash in ID order. Defaults: every field's default is its zero value, so `defaults.go` appends nothing and no default macro constant exists (N-027). Source: MON 4.1, 11, spec-config 3.1, 8.2.
- **D327.** One new helper in `internal/checked`: `MulAddDivSat(a, b, add, c)` for non-negative arguments returns `q = floor((a*b + add) / c)` saturated at `math.MaxInt64` and the exact remainder `r`, with the numerator in 128 bits. A grant forms `w*Amount` with `checked.Mul` (at most `MaxMoney`) as `a` and passes `b = S`; a rate levy passes `a = base` and `b = RateBP*S` (formed by `checked.Mul`, at most 10^9), so the numerator reaches 10^23 for a grant and 10^27 for a levy, both inside 128 bits (owed: MON 6.4.1 gives 10^23 only). The caller treats a quotient at or above `MaxMoney` as `MaxMoney` (MON 6.4.1). Source: architecture 3.5 (the one shared 128-bit helper), MON 6.4, FR-MON-017.
- **D328.** When a recipient's due is cut by two bounds, the room bound acts first (a levy's available balance `Short`, a grant's headroom `Headroom`), then the flow's remaining limit (`Limit`); a household is counted in the first count that cut it only, so `Short + Headroom + Limit` never exceeds the households short of their due. MON 5.4 and 13.1 are silent on both binding (owed edit). The carry advances by the due in every case (FR-MON-022).
- **D329.** The carry of a flow is a slice indexed by `AgentID` with a "started" bit, started at the recipient's first visit by the flow with `StartCarry` (`(accountID mod P) * 10^4` for a rate grant and a fixed levy, 0 for a rate levy; MON 6.2). The start value is a function of the account ID alone, so a lazy start equals a start at creation. An agent that leaves the class keeps its carry and resumes it on return (MON 4.3.1: "moves between classes with its carry"); a removal drops it (D331). Only started carries of open accounts are saved, in ascending account ID (tag 13). Owed: MON 14 and spec-checkpoint 4.2 tag 13 say "open accounts" and must say "started".
- **D330.** The class scan runs once per tick, only when some flow is active: one pass over `w.agents` in ascending `AgentID` (which is ascending account ID: both are assigned in creation order) building per-region slot lists in scratch held by the module, skipping agents of weight 0 (estate pseudo-agents and removed slots). Membership is read from the agent's role and the region of its account at that moment (FR-MON-007, 009). Each flow then walks regions in order and its role's agents in the lists. Cost: O(agents) per tick plus O(recipients) per flow (NFR-MON-002).
- **D331.** P1.7 is a `line` position: `tick.go` appends `P1.7 MON line` to `positionList` in table order of spec-world.md 6 (after P1.6 when it exists, before P1.7a and P1.8), deletes `P1.7` from `notBuiltPositions`, and the straight line calls `w.p17Flows()` under `if w.money != nil` (the guard form of architecture 2.10.3, established by plan 5). `p17Flows` has no error result: a ledger refusal of an amount that was checked against the balance, the headroom and the limit is a violated invariant and panics with the message of `invariant` (MON 5.4, architecture 8.1). The replay rows of poshash_internal_test.go gain the guarded `replayRows` row `{id: "P1.7", on: w.money != nil}` so an off world records no line (without it `checkRows` fails with "position P1.7 of tick.go has no method in the replay map"), and `observe_internal_test.go` gains the `stepSites` row for P1.7, after P1.6 (after P1.2 if plan 7 is not merged) and before P1.8, which `TestCallSites_TheTableIsTheStraightLine` requires.
- **D332.** The income term is one core accessor, `welfareScratch.addUnearned(slot, amount)` in `welfare.go` beside `addReceipt` (the `unearned` field `G_t` and `Record.Unearned` already exist and nothing writes them). A grant to households that is not `NotIncome` adds its applied amount to the recipient's slot (slot = `AgentID`); a levy and a `NotIncome` grant add nothing (MON 7.2, FR-MON-025, WEL 2.1.9). It is read at P6.3 of the same tick, so a grant of P1.7 counts in that tick's income.
- **D333.** `World.Audit` and `p84Audit` each call one function, `w.auditModules()`, defined in `moneyflow.go` for now: for each flow, `Total` equals the absolute boundary balance of its reason with the sign of its kind, and the first flow that disagrees is named (FR-MON-026, 027). A restore runs it through `Audit` (spec-checkpoint 6.2 step 10). The call site is a module touch point outside the catalogue files, which architecture 2.10.2 does not list (owed: the audit hook is in plan 5's consolidated edit of 2.10.1, 2.10.2 and 2.10.4, with the D333 wording supplied there; `auditModules` stays in `moneyflow.go` as owner).
- **D334.** Three events in `event.go` with the fields of observability 4.1 (`MoneyFlowLimited{Tick, Flow string, Region RegionID, Due, Applied Money, Short, Headroom, Limit int64}`, `MoneyFlowEnded{Tick, Flow string, Cause Cause, Total Money}`, `MoneyFlowScaled{Tick, Flow string, From, To int64, Cause Cause}`), and the constants `CauseLimit` and `CauseCap` (`CauseConsumer` exists; `policy` is PLC's). Emitted after both passes, per flow in ascending ID: for each region ascending the `MoneyFlowLimited` when `Due != Applied`, then the flow's `MoneyFlowEnded` (observability K7). Built only when an observer was supplied; counters are integer additions into preallocated slots. Debug lines "money flow limited", "money flow ended", "money flow scaled" with keys `flow`, `region`, `due`, `applied`, `cause`, `from`, `to`, guarded by `Enabled`; no Info, Warn or Error from the step (FR-MON-032). The keys `flow`, `due`, `applied`, `from`, `to` are added to `internal/logkeys` (their rows are in rules 3.3.2 already).
- **D335.** The flow scale is state in `moneyFlows` (default 10 000, 0 to `MaxFlowScale`), not hashed, saved in tag 13. The internal setter `setFlowScale(i int, bp int64, cause Cause) error` validates the bound (`ErrOutOfBounds`), changes nothing when equal, emits `MoneyFlowScaled` with `Tick = w.Tick()` and applies from the next P1.7. The public call `SetFlowScales`, `ErrModuleOff`, the unknown-flow lookup by ID and `ErrInStep` are plan 17's; the sentinel `ErrUnknownFlow` is declared here because the flows are this module's. Source: MON 4.4.3, 10.4, FR-MON-023.
- **D336.** Snapshot: `Flows []FlowRow{Flow string, Total Money, ScaleBP int64, Ended bool}` appended at the end of `Snapshot` (observability 5.3.3), empty with the module off; `Boundary` rows follow D323(b); `modulesOn` returns `money_supply` (the snake-case name of the `Modules` key, as the file spells it; the rule text "lower-case name" is ambiguous, owed). `RegionRow` gets neither `MoneyContract` nor `MoneyTreasury` (their modules append them, observability 5.3.2); FR-MON-042 is met for the fields that exist.
- **D337.** Tag 13 body, in the order of MON 14: per flow in ID order `Total`, `Scale`, `Ended` (0, 1 limit, 2 cap); then, per flow with a household target and a carry shape (rate grant, fixed levy, rate levy; a top-up has none), the started carries as (account ID, carry) pairs in ascending account ID, open accounts only. The pool case (one carry per region) is plan 7's and is written after the household pairs of the same flow. Decoding checks R6 (indexes), R8, R9 (strict ascent) and cross-check 7 ("every money-flow carry is for an open account").
- **D338.** Warnings built here, through `warnings(c *Config)`, never failing validation, each with its path `modules.money_supply.flows.<id>`: `no_flows`, `faucet_without_sink`, `pair_unbalanced` (tolerance 1 000 basis points, a rule constant), `levy_below_upkeep` (one tick of the targeted role's effective upkeep at the reference prices, via `effectiveUpkeep` and `listCost`), `class_empty`; `class_without_income` (plan 5) is not raised for a role that a grant to households with `NotIncome` false targets, so this plan appends that exemption to `hasIncomeSource` (FR-DEM-033, MON 12.2). `grant_to_pool_no_outlet` is plan 7's, `store_levy_below_upkeep` STO's. A rate levy is outside `pair_unbalanced` (MON 9.2).
- **D339.** N-314, what MON can do and what it cannot (this plan builds none of the pack, plan 8 does). The slice has no channel for the cooks' money to return, and the demand module (plan 5) is the owner's answer. The MON flows that could return money to the other roles are: (1) a rate levy on the cook role with `Exempt` at the role's reserve (MON-D2, a holding charge, bounded by `m* = E + g/rho` for a household that spends nothing, MON 9.3); (2) a rate grant, or a top-up to `Level = ReserveTicks * U_c`, to the growers and other roles with income below upkeep; (3) the two as a pair, the levy paying for the grant by nominal totals (MON 9.2). A flow is a transfer through boundaries, not a purchase, so it returns money without creating the demand that sells the goods, and the pair drifts `M` by its difference (a mirror levy was rejected, MON 21 item 6). What plan 8 needs from this plan: the two overlays and the households target by role and region (Provides, through the types); the `NotIncome` rule, because a grant that counts as income raises the grower's welfare ratio above its target and the target-income rule then rests it (MON 7.2), so a grant to a producer role wants `not_income = true` unless the plan wants it to rest; the warning `pair_unbalanced` as the check of a sized pair; and, for a levied class, a warm `Money` at or below `m*` (MON 15.4, an optional VIA edit). The sizes (about 550 a grower household-tick against a levy on 136 cooks, from N-314's 45% and 138%) are plan 8's to derive from the re-solved census, and its Phase 1 decides first whether the demand module alone suffices.
